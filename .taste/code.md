# 代码怎么写

## 让算法看得见

- 读代码的人应该一眼看出算法：一个函数对应论文里的一个公式或算法的一行，docstring 写明对应编号。
- 变量名跟公式走（`a`、`lam`、`plan`、`cut`），矩阵的变量顺序在注释里写一次（`[a (N), lambda (2), g (N)]`）。
- 一个模块做一件事；核心算法保持少量文件。实验、数据生成、基线和报告放在核心之外。

## 不要防御性工程

- **不写防御性代码。** 不为“可能发生”的情况加检查、修复、回退和余量；只处理真实出现过、能复现的问题。
  例：HiGHS 的两个已知求解错误，集中在一个包装函数里处理，并写清原因。
- 不加兼容层、旧接口别名、`try/except` 吞错误、层层 `if x is None`。旧代码不用了就删。
- 输入检查只做用户真会犯的错（参数范围、形状），在入口处一次完成。
- 不为“严格证书”“数值安全”额外搭一套修复流水线；需要可靠的界时，用数学上更直接的构造
  （例如把乘子补成可行解），而不是在近似解上打补丁。

## 测试

- 测试检查数学：与独立实现（例如直接写的运输 LP）比对数值，检查界的方向、割在所有点上的有效性、解析例子。
- 不测实现细节和内部私有函数的调用顺序。
- 测试名说出被检查的性质（`test_ratio_cuts_are_valid_on_every_subset`）。

## 风格

- 行宽不超过 100；能用一行清楚表达就不拆成三层抽象。
- 注释解释“为什么”，不复述代码。
- 结果里记录模型版本；改变算法或结果含义时升级版本号。
- 改完运行全部测试；数字写进文档或笔记之前，确认它来自当前代码的真实运行。
